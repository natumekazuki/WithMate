# UI Design Guidelines

WithMateのUI設計・変更・reviewに適用する、画面横断のデザイン原則と共通パターンの正本。個別の画面やIssueによらず、表示と操作を判断する基準を定める。

製品の目的と優先順位は[Product Direction](product-direction.md)、各Windowの画面構成・固有の操作条件と現行動作は[Desktop UI](desktop-ui.md)と[Settings UI](settings-ui.md)を参照する。この規約は設計・変更の基準であり、各画面の実装・検証状況を示すものではない。

## デザイン原則

### 情報の優先順位

- 会話、ファイル、差分、要求本文など、その場で読む・判断する対象を主内容とし、操作や状態表示は対象との関係が分かる位置と強さで配置する。
- 同じ事実を見出し、label、status、helper文で重ねない。正常状態や操作を言い換えただけの常設説明は省略し、error、validation、安全、回復に必要な情報は残す。
- 情報を短くすること自体を目的にせず、対象の識別、判断材料、失敗の理由、次に可能な操作を失わない。

### レイアウトの安定性

- 非同期処理や一時的な状態表示によって、操作対象・閲覧中の内容・周辺の配置を意図せず移動させない。状態表示に必要な領域を確保し、利用者の操作位置と読む位置を保つ。
- 読込中から内容表示への切り替えや、一時的な通知の出現・消失でも、隣接する操作や内容を不用意に押し出さない。失敗や回復に必要な情報を隠して安定性を保ったことにはしない。
- 利用者による展開・折りたたみ、画面幅や文字サイズに応じた再配置は、その操作や内容の意図に沿って行う。安定性は、すべての部品を同じサイズにすることや、内容を固定寸法へ切り詰めることを意味しない。

### 一貫性と視認性

- 同じ役割には共通の表現と振る舞いを使い、既存のtheme token、CSS variable、共通primitiveとcomponentを優先する。画面の目的が違う場合も、用語、状態の意味、操作の手掛かりを揃える。
- surface・badge・button等の色を扱うときは、その上のtext・icon・borderのcontrastを同時に確認する。disabled、muted、placeholder、secondary textと、hover、selected、active、focus、error、warning、successの状態も背景へ埋もれないようにする。

### 操作とアクセシビリティ

- 操作名と対象、focus、busy、選択・toggle状態を、見た目と支援技術の両方へ伝える。色やmotionだけを状態の唯一の手掛かりにしない。
- native control、keyboardでの到達と操作、visible focus、accessible nameを維持する。icon-only controlにも具体的な操作名を持たせ、hoverしなければ操作や意味が分からない構成にしない。
- 処理中の操作制御は実際の処理範囲に合わせる。同一処理の重複実行は必要な範囲で防ぎ、無関係な操作や利用可能な取消・回復まで一律に止めない。

## 共通パターン

### 表示言語と文言

- アプリ内UIのユーザー向け表示文字列は英語を標準とする。Character定義、ユーザー入力・生成コンテンツ、provider向け指示、ログ、テストデータ、開発者向け文書は対象外とする。
- アプリ所有の短い表示文、見出し、label、button、option、status名は単語間に空白を入れたTitle Caseを使う。長いerror・safety説明、screen reader向けの自然文、ユーザーが入力・生成する内容は読みやすい文章を維持する。ブランドとAPI / CLI / JSON / MCP / URL / HEAD等の正式表記は維持する。
- 検索inputのplaceholderは表示せず、accessible nameは残す。
- 会話、ユーザーtitle、Character定義、テンプレート本文、ファイル内容・path、raw診断、Provider指示は原文と保存値を維持する。表示用の日時・件数には英語localeを明示し、ローカルtime zone、保存値、parse、sort、raw copyを変更しない。UI用の通常状態copyは各consumerが定義し、ユーザー設定として編集・保存しない。
- `Stop`はrunの停止要求、`Cancel`は現在操作の取消、`Close`はWindow等を閉じる操作、`Quit`はアプリ終了と区別する。

### ボタン

- 通常時は、対象が明確なtoolbar操作に既存iconを使う。Save等の主CTA、Approve / Reject、Forget、GC、全削除、最終確認には、判断に必要な可視labelと影響説明を保つ。
- 操作ボタンの処理中は、通常時に確保した領域の中をスピナー単独表示へ切り替える。文字や通常iconの横にスピナーを追加したり、処理中文字列へ置き換えたりしない。通常時・処理中・終了後で、そのボタンの外寸・位置と周囲の配置を変えない。
- 視覚的にlabelを隠しても、支援技術へ操作名・対象と処理中状態を伝える。処理中は重複実行を防ぐ必要がある操作のcontrolをdisabledにし、成功・失敗後に実際の操作可否へ戻す。利用条件によりdisabledなだけのボタンと、処理中のボタンを混同しない。
- 個々のボタンは用途と内容に合ったサイズを持つ。状態切り替えの安定性を、全ボタン共通の固定幅や固定高さで代用しない。

### 読込・空・失敗

- 状態表示は通常のlayoutと配色を既定とする。初期化・開始待ち・処理中・未取得だけを理由にerrorの枠・配色・文言・alertを出さず、必要な待機表示を保つ。対象処理の失敗が明示的に確定した場合だけerror表示へ切り替え、成功・完了の表示も成功が確定してから行う。「成功が未確認」を失敗の判定条件にしない。
- 失敗の判定と表示は対象処理・request単位で行う。実行記録の取得失敗を実行そのものの失敗へ読み替えず、結果不明を成功・失敗へ寄せない。確定済みの失敗、入力不正、権限不足、安全・回復に必要な説明と操作は待機表示で隠さない。
- 読込状態はパーツ単位で持ち、必要なデータが揃ったパーツから表示・操作できるようにする。再取得中や失敗時も取得済みの内容を保持し、無関係なパーツを画面全体のgateで隠さない。
- データの読込中は共通の[LoadingIndicator](../../src/ui/loading-indicator.tsx)を使い、対象を示すaccessible statusと`aria-busy`を持たせる。既存の専用skeletonや実行・保存操作のbusyとは区別する。
- 未取得、pending、利用不可、正常0件、失敗を区別する。別の対象・request、一覧取得とrun、内容とdetail取得の状態を混ぜず、同一対象・同一requestの待機表現を集約する。
- 正常0件、検索0件、情報のないpane/listの本文は空にする。既存shell、必要な見出し、create/restore等の操作、accessible nameは残し、未取得・読込中・取得失敗は正常0件と混同しない。読込中は対象領域のspinnerとaccessible status/busyへ集約し、取得失敗は対象パーツへ理由と再試行導線を置く。

### フィードバックとmotion

- 承認・入力待ちは次の操作と要求本文を示す。未保存・保存中・失敗・回復を区別し、新しい編集に古い保存成功を表示しない。
- 局所的なmotionを使い、reduced motionではspinnerを停止し、止まった形状とaccessible statusでも状態を識別できるようにする。
- spinnerのために処理完了を遅らせない。通知は意味のある遷移へ絞り、会話本文や全カードを重複して読み上げない。

## 変更時の確認

変更した部品とその影響範囲について、通常・処理中・成功・失敗の必要な状態遷移、keyboard操作、accessible name・busy stateを確認する。狭幅、長いlabel、文字拡大、reduced motionは、その変更で影響を受ける条件を選ぶ。

実質的なUI変更では、実描画と操作で外寸、周囲の配置、読む位置、focusと操作可能性を確認する。test/buildの成功だけで視覚品質を確認済みとせず、実施した確認と未確認を分けて報告する。
